# Agent Note: 预留空间是元素，不是长度

Status: implemented

[English](2026-08-19-reserved-room-runs.md) | 中文

## 问题

`ui-keybindings` 里有两处界面各自手工长出了同一套布局，各自带着一组硬编码宽度。列标题为排序标记预留空间，这样给某列加排序时标签不会移位；录制条在末端为确认与取消控件预留空间，这些控件浮在条带之上，且绝不能盖住最后一段按键。两处都是由一批以像素计数命名的自定义属性搭起来的——`--dsh-sort-mark`、`--dsh-heading-gap`、`--dsh-sort-slot`、`--dsh-recorder-control`——外加按它们取尺寸的 `::before`/`::after` 占位元素。

这些数字里的每一个都是一个待发生的谎言。它们重述了浏览器本就知道、且会随字体、语言环境、缩放以及标记自身内容而变的宽度：一个多出排名数字的排序标记所需的空间比那个常量更大，而没有任何东西会报告这种不一致。列标题的规则比常量更糟，因为它是有条件的——未排序时在两侧余量各预留 `calc(--dsh-sort-slot / 2)`，排序后又把整块槽位聚到末端——而两处界面又以不同形态表述同一份预留，于是修好一处并不会惠及另一处。

## 决定

行（run）把预留空间表述为一个**元素**：调用方传入 `reserve`，即该端所能容纳的最宽形态，行把它隐藏渲染。由引擎来测量。`Run.module.css` 里没有任何规则携带长度，也没有任何代码做测量——没有 `ResizeObserver`，没有布局读取，除 React 本就持有的之外没有任何状态。

fitted 行由**两个平面**构成，因为一个元素无法同时决定行索要多少宽度、以及东西摆在哪里。

**尺寸平面**就是行自身：两个隐藏样本——内容的影子与 reserve——放在两条 `max-content` 轨道上。它们是流内仅有的东西，因此行索要的宽度恒为内容加上预留空间。占位者不是这份索要的输入，因为它根本不在这个平面里。这比"分别测量有无占位者两种状态并发现二者相等"更强：这里只有一种状态。

**绘制平面**是一层覆盖层（`position: absolute; inset: 0`），按尺寸平面争得的宽度布局。它承载读者看到的内容、预留空间与占位者，并且可以按对齐要求随意摆放它们，因为它所做的一切都回不到尺寸里去。预留空间是否被占用，是这个行拥有的唯一状态：`occupant` 是站在里面的那个东西，而 `occupied` 表示它被行并不持有的某物占据——比如浮在行末端之上的控件，它无法嵌套进自己所浮盖的内容里，于是行只为它让路而不持有它。空着时，内容在整个行的范围内遵循所设的对齐。被占用时，该平面变为余量、内容、预留空间三条轨道，其尾部轨道以 reserve 兜底。于是内容落在

$$\min\!\left(s,\ \frac{R + s}{2}\right)\quad\text{其中 } s = W - L - R$$

这是一条公式，而不是一串情形：只要还有可居中的余地就居中，偏离也恰好只偏离标记所需的那么多，而当富余达到预留空间的宽度时便完全不动。

### 为什么必须要两个平面

在 grid 中，两个项的内在贡献只有在其轨道跨度彼此不相交时才相加。设行索要的宽度恰为 `L + R`，且这份索要由内容与 reserve 共同提供。那么它们的跨度就是铺满 `[0, L + R]` 的两段不相交区间，长度分别至少为 `L` 与至少为 `R`，等号成立便迫使内容的跨度只能是 `[0, L]` 或 `[R, L + R]`。而居中的内容需要其跨度自 `R/2` 起始——两者皆非。因此，只要内容在流内、且索要由内容与 reserve 共同提供，在下限处居中就是不可能的；没有任何分布模式、`fit-content`、subgrid 或书写模式的安排能够绕开，因为它们移动的都只是轨道边界，而没有一个能改变"相加要求不相交"这一点。

这个阻碍约束的是**内容**，而不是那份**索要**。重叠是绘制层面的事实，不相交是尺寸层面的事实；出路便是不再让同一个元素同时干这两件事：把可见的内容移出流，让它的一个隐藏影子来提供 `L`。因此影子恰是 reserve 的镜像——reserve 表述预留空间的宽度，影子表述内容的宽度——它是必需之物，而非取巧。

尺寸平面的两条轨道用 `max-content` 而非 `auto`：`auto` 作为最小值指的是**自动**最小尺寸，任何 `overflow` 不为 `visible` 的项都会放弃它，而内容会省略号截断的调用方说的正是这件事。届时行将只索要预留空间那么宽，一列便可被拖得比它自己的标题还窄。实测：用 `auto auto` 时，`width: min-content` 的外框给出 32，而 `L + R` 为 70.89——而表格正是通过在标题单元格上设 `width: min-content` 来取得每列的拖拽下限的。

## 实测行为

在 Chrome 150 中针对真实页面测得。列宽在未排序、加一个排序、两个排序带排名、以及全部撤销这四种状态下逐字节相同——`216.906 / 140.344 / 261.016 / 71.1719 / 76.5625`——因此没有任何状态变化会移动某一列。下表的偏移量是标签中心相对其单元格中心的位移：

| 列 | 高出下限的富余 | 未排序 | 已排序 | 带排名 |
| --- | --- | --- | --- | --- |
| Priority | 0 | 0 | −16.7 | −16.7 |
| Source | 8.39 | 0 | −13.2 | −13.2 |
| Keybinding | 充裕 | 0 | 0 | 0 |
| When clause | 充裕 | 0 | 0 | 0 |

Priority 恰好位于它的下限，因此它的标记取走了自己所需的全部空间；Source 尚余 8.39，位移便更小；宽的两列则完全不动。这正是上面那条公式，从页面上读出来的样子。

针对一个载有实际发布样式表的探针页面，取 `L = 38.89`、`R = 32`：在未被占用、占位者窄于 reserve、占位者与 reserve 等宽这三种情况下，行的宽度在每一种外框宽度下都相同——包括 `min-content` 与 `max-content`，二者均给出 70.89 = `L + R`。内容的中心偏移：

| 行宽 | 未被占用 | 已被占用 |
| --- | --- | --- |
| `min-content` / `max-content`（70.89） | 0 | −16 = −R/2 |
| 71.17（下限） | −0.01 | −15.87 |
| 87.87（下限 + R/2） | 0 | −7.52 |
| 104.56（下限 + R） | 0 | **0** |
| 137.95、300 | −0.01 | −0.01 |
| 55（低于下限） | −0.01，未裁剪 | −8.05，未裁剪 |

`justify` 的 `start`、`end`、`stretch` 在两种状态下均已验证：`start` 始终把内容顶在起始端；`end` 在未被占用时把它顶在末端，被占用时则抵住预留空间；`stretch` 未被占用时铺满整个行，被占用时铺满行减去预留空间的部分。

滚动行在同一页面上测得，所用录制条宽 122.34、其中按键块宽 76.70、预留空间为 25。空闲时两侧余量为 22.81 与 22.83，按键块偏离居中 0.01；画出控件后两者变为 20.64 与 25，按键块移动 2.18，与控件之间尚余 11；控件消失后一切复原。全程表格各列读数为 `216.906 / 140.344 / 261.016 / 71.1719 / 76.5625`。收窄以迫使滚动后，轨道为 `0 / 76.70 / 25`，可滚动量 50，而滚到该尽头时最后一个按键块与控件之间尚余 11.3。

## 考虑过的替代方案

- **用 `anchor-size()` 从占位者推导预留量**：有证据地否决。`CSS.supports('width', 'calc(anchor-size(--x inline) / 2)')` 在 Chrome 与 Librewolf 中都返回 true，看上去可用；但对查询方与锚点各自定位方式做的探针矩阵显示，它只在**查询方**为绝对定位时才解析（`absQ_absA` 为 20，`absQ_staticA` 为 20，所有 `staticQ_*` 均为 0，且 `position-anchor` 也无济于事）。绝对定位的盒子不占流内空间，因此它永远无法充当推开内容的那个占位元素。
- **用 `ResizeObserver` 测量并写入自定义属性**：否决——它把 CSS 方案所去除的可变状态又请了回来，比它所描述的布局慢一帧，并且把预留从事实变成了副作用。
- **保留像素常量并加一道门禁**：否决——没有哪道门禁能拿一个它并不渲染的字体去核对常量。这种不一致只有在浏览器里才看得见，而那正是常量出错的地方。
- **用 flexbox 加一个 `flex: 1` 的占位元素**：否决——占位元素的基础尺寸会并入容器的 `min-content`，于是行的下限恰好长出了它本该能够交出的那段富余。
- **对称预留，两侧余量各放一份隐藏副本**：在任何宽度下都居中，但下限变为 `L + 2R`——Priority 将从 71.17 变成 104.56，而这些宽度要从更宽的列那里拿。
- **单平面：把 reserve 的最小贡献清零，再用 `min-width: max-content` 恢复下限**：实测确实完美居中，但也实测把下限照样翻倍到了 `L + 2R`，因为 grid 的内在尺寸会把各 `1fr` 轨道统一放大到贡献最大的那条，从而把空着的前侧余量吹到 reserve 那么宽。
- **单平面，改用 `auto` 余量加 `justify-content: center` 以避开这种统一放大**：此时 max-content 确实是 `L + R`，但在该宽度下，富余空间会被尾部 `auto` 轨道增长到自身 max-content 所吃掉，内容于是又顶到了起始端。把该轨道封顶为 `0` 能阻止它吃掉空间，同时也阻止了它做出贡献，下限便坍缩成 `L`。
- **把 reserve 内联放进内容包装元素之内**，使内容轨道的 min-content 成为 `L + R`：下限正确且没有统一放大，但内容坐在该包装元素的起始处——同一份偏移，只是换了个位置。
- **让内容留在流内、跨越全部轨道，再用一个影子撑住前侧余量**：未被占用时完美居中，且完全不改动被占用状态；但被占用模板的 `1fr` 余量会让行的 max-content 成为 `L + 2R`，于是由 max-content 驱动的消费方——`width: max-content` 的外框、auto 布局的表格——会在排序时把该列撑宽整整一个预留空间。实测 104.52 对 71.14。

## 影响

预留量现在跟着自己的内容走：给标题一个带排名的标记，空间就按带排名的标记来留，没有任何东西需要更新。两处界面从同一个地方得到同一份行为，而 `ui-keybindings` 迁移到它们之上后，会去掉四个自定义属性和它的占位伪元素。

代价有三，且都是由调用方遵守、无人核查的约定。fitted 行会把内容渲染两次，因此两次必须测得一样：应是一段短语，而不是带 `id` 的子树，且其换行不应取决于自己是哪一份副本。滚动行在这一项上不付任何代价，因为它索要的只有预留空间——这也正是录制器那条按键块条（它是子树而非短语）用滚动行而不是 fitted 行的原因。`reserve` 必须是该端所能容纳的最大形态，因为比它更大的占位者会溢出分给它的空间，而不是把空间撑大。此外，行现在会在自身上声明 `position: relative`、在其覆盖层上声明 `position: absolute; inset: 0`——这是加在行自己拥有的元素上的布局管路，不绘制任何东西也不陈述任何长度，但确实超出了这个原语起初"只有轨道与区域"的范围。

测试套件只钉住标记结构。jsdom 不解析布局，因此规则本身在浏览器中验证并记录于上面几张表；轨道模板的回归能通过单元测试。这是一处有意的划分，而不是一道该用无头布局引擎去补的缺口：这些论断谈的是真实引擎如何处理内在尺寸。

`ScrollingRun` 分的是同样两件事，但它的两个平面是叠放而非分层的：滚动容器必须留在流内，才能给出行的高度、也才能让内容有自然的行。它的盒子只索要预留空间，别无其他，这对滚动容器而言才是诚实的索要——它对装不下的内容的全部回应就是滚动，因此再放一个内容的影子，只会把任何人曾放进去的最长内容的宽度硬塞给这一列。隐藏的 reserve 站在盒子那唯一的单元格里，两种状态下索要都由它而来；旁边的滚动容器什么也不索要，因为它自身的 overflow 已经交出了自动最小尺寸。

滚动容器内部只在预留空间被占用时才放入它，正是这一点让它空着时两侧余量保持相等。这也是两种行在行为上、而非构造上唯一真正不同之处：可滚动范围会随预留空间一同变化。预留空间到来时范围增长，离开时范围收缩——而收缩的范围会让引擎把任何越过新末端的偏移量夹紧，位置就在我们的任何代码读到它之前被丢弃了。这一丢失发生在离开的路上、而不是回来的路上，正因如此它容易被误诊。

因此录制器会在预留空间尚在时把偏移量记下来，并在它回来时还回去，且只对仍然停在夹紧位置上的条带作还原。在收窄以迫使滚动的条带上实测：停在 50 范围中的 42 处，控件的尾部间隙为 3.3；取消悬停后范围降至 25，引擎把偏移量一并移到 25；重新悬停后偏移量回到 42，按键块回到它原本占据的那一像素。在控件离开期间被移动到 5 的条带则停在 5。改为跟进到末端同样能让开控件，但已被否决：这段余地的存在本就是为了让条带不要移动，而在其中整整跳动一个预留空间，恰恰背离了它的用意。

计划中的 2D 行从 fitted 这一侧迁移：尺寸平面变为 3×3 的隐藏样本，各贡献按同一条不相交规则逐轴相加，覆盖层则运行同样的逐轴模板，每条预留边各有一个独立的开关。
