# Agent Note: 预留空间是元素，不是长度

Status: implemented

[English](2026-08-19-reserved-room-runs.md) | 中文

## 问题

`ui-keybindings` 里有两处界面各自手工长出了同一套布局，各自带着一组硬编码宽度。列标题为排序标记预留空间，这样给某列加排序时标签不会移位；录制条在末端为确认与取消控件预留空间，这些控件浮在条带之上，且绝不能盖住最后一段按键。两处都是由一批以像素计数命名的自定义属性搭起来的——`--dsh-sort-mark`、`--dsh-heading-gap`、`--dsh-sort-slot`、`--dsh-recorder-control`——外加按它们取尺寸的 `::before`/`::after` 占位元素。

这些数字里的每一个都是一个待发生的谎言。它们重述了浏览器本就知道、且会随字体、语言环境、缩放以及标记自身内容而变的宽度：一个多出排名数字的排序标记所需的空间比那个常量更大，而没有任何东西会报告这种不一致。录制条的规则比常量更糟，因为它是有条件的——移动足以避免滚动时条带就移动内容，不足时才滚动——而两处界面又以不同形态表述同一份预留，于是修好一处并不会惠及另一处。

## 决定

行（run）把预留空间表述为一个**元素**：调用方传入 `reserve`，即该端所能容纳的最宽形态，行把它隐藏渲染在 `occupant` 落入的同一个网格单元里。由引擎来测量。`Run.module.css` 里没有任何规则携带长度，也没有任何代码做测量——没有 `ResizeObserver`，没有布局读取，除 React 本就持有的之外没有任何状态，因为占位者在场时的几何关系与单元里只有 reserve 时完全相同。

`FittedRun` 排布三条轨道：前侧余量、内容、预留端。余量是 `fr` 系数，另两条以内在最小尺寸兜底，这就固定了空间被交出的顺序。空间紧张时，行先花掉余量——居中是第一个牺牲品——余量用尽后，它宁可溢出所在单元，也不裁剪内容或交出预留空间。这个顺序就是全部策略，并且在每种 `justify` 模式下都成立，因为没有任何系数能触及某条轨道的最小尺寸。

`ScrollingRun` 把 reserve 渲染两次，一次作为内容之前可坍缩的富余，一次作为内容之后固定的预留空间，放在一个滚动容器里，该容器在内容装得下时收缩包裹、装不下时填满其盒子。它的模板就是把 fitted 的那套反过来讲：内容轨道与预留轨道以各自的 `max-content` 兜底，于是富余空间唯一能到达的轨道就是那段可坍缩的富余。仅此一个事实就生成了完整的"先移动、后滚动"规则。只要还有余地，富余就吃掉它，内容保持居中；余地耗尽的过程中，富余逐步交还，内容随之向前端漂移；富余归零后行开始滚动——而它在让步于滚动之前所移动的余量，恰好就是 reserve 的宽度，一个无人选定、也无人需要维护的值。

用 grid 而非 flex，是为了 flex 没有的一条性质：`1fr` 轨道即 `minmax(auto, 1fr)`，轨道的最小尺寸与它在富余空间中的份额是彼此独立的量。而 flex 项的基础尺寸会计入其容器的 `min-content`，于是以 flex 项表达的富余被记到了下限上：居中将要付出第二份预留的代价，而且行会拒绝变窄。

## 实测行为

在 Chrome 150 中，针对一个载有实际发布样式表的探针页面测得，盒宽 320px，reserve 宽 48px。绝对数值依赖字体，各项关系不依赖。

| 情形 | 内容宽 | 富余 / 内容 / 预留 | 可滚动量 | 滚到尽头时 |
| --- | --- | --- | --- | --- |
| fits | 66.56 | 48 / 66.56 / 48 | 0 | — |
| near | 207.69 | 48 / 207.69 / 48 | 0 | — |
| move | 242.97 | **29.03** / 242.97 / 48 | 0 | — |
| edge | 278.25 | 0 / 278.25 / 48 | 6 | 内容末端落在控件边缘 |
| over | 436.19 | 0 / 436.19 / 48 | 164 | 内容末端落在控件边缘 |

`move` 这一行就是规则在起作用：富余从 48 中交出了 18.97，好让内容仍然装得下，而 `scrollable` 为 0。最后两行则是预留空间兼作过滚区——滚到最大位置时，内容的尾边缘落在浮动控件前边缘的四分之一像素以内，两种书写方向下皆然（RTL 滚动到 −164，测得的数值相同）。

对 fitted 行而言，下限是 `0 / 45.38 / 48`，且在有无占位者两种情况下逐字节相同，这正是整套设计所要的那份不变性。320px 的盒子给出 `137.31 / 45.38 / 137.31`，有占位者时同样相同。120px 的盒子给出 `26.63 / 45.38 / 48`——余量已部分花掉，预留空间完好。60px 的盒子比内容加预留还窄，给出 `0 / 45.38 / 48`，内容未被裁剪，行改为溢出。`justify="end"` 把全部富余移到前侧余量，`justify="start"` 移到后侧，`justify="stretch"` 则把它交给内容（`0 / 272 / 48`）。

有五条声明看着像承重的，其实不是；在探针显示去掉它们后完整的 19 个用例矩阵没有变化之后，它们被删除了：内容上、滚动容器上、以及滚动容器摆放盒上的 `min-width: 0`，还有富余元素上的 `min-width: 0` 与 `overflow: hidden`。每套模板都显式给出了轨道最小尺寸，因此项自身的自动最小尺寸从不被采纳；坍缩后的富余向行内起始方向溢出，那是滚动到不了、`scrollWidth` 也不计入的方向。唯一承重的那个 `min-width: 0` 在 fitted 行自身上——没有它，位于 `1fr` 单元中的行会把各轨道之和作为自动最小尺寸带进去，而这样的列会拒绝被拖窄到底。

## 考虑过的替代方案

- **用 `anchor-size()` 从占位者推导预留量**：有证据地否决。`CSS.supports('width', 'calc(anchor-size(--x inline) / 2)')` 在 Chrome 与 Librewolf 中都返回 true，看上去可用；但对查询方与锚点各自定位方式做的探针矩阵显示，它只在**查询方**为绝对定位时才解析（`absQ_absA` 为 20，`absQ_staticA` 为 20，所有 `staticQ_*` 均为 0，且 `position-anchor` 也无济于事）。在流内的轨道无法据此取尺寸，于是这项特性检测是个陷阱：它报告支持某个语法，而该语法在我们需要的场景下悄然得出零。
- **用 `ResizeObserver` 测量并写入自定义属性**：否决——它把 CSS 方案所去除的可变状态又请了回来，比它所描述的布局慢一帧，并且把预留从事实变成了副作用。它也表达不了其中有条件的那部分：先移动后滚动的余量又会变回一个显式数字。
- **保留像素常量并加一道门禁**：否决——没有哪道门禁能拿一个它并不渲染的字体去核对常量。这种不一致只有在浏览器里才看得见，而那正是常量出错的地方。
- **用 flexbox 加一个 `flex: 1` 的占位元素**：按上文那条性质否决——占位元素的基础尺寸会并入容器的 `min-content`，于是行的下限恰好长出了它本该能够交出的那段富余。
- **一个组件加一个 `scrolling` 开关**：否决——两者在轨道模板、reserve 渲染的位置、盒子是否收缩包裹、以及哪些 `justify` 模式有意义这四点上都不同。开关将会命名两套布局的并集，而 `stretch` 会在那个无法兑现它的布局上也可拼写。

## 影响

预留量现在跟着自己的内容走：给标题一个带排名的标记，空间就按带排名的标记来留，没有任何东西需要更新。两处界面从同一个地方得到同一份行为，而 `ui-keybindings` 迁移到它们之上后，会去掉四个自定义属性和它的占位伪元素。

代价是一份由调用方遵守、且无人核查的约定：`reserve` 必须确实是该端所能容纳的最宽形态。比自己的 reserve 更宽的占位者会把预留轨道撑大，而这也是占位者出现时唯一可能让行发生位移的情形——恰恰是这套设计本要排除的那种失败。它被写作包 README 里的一条限制，而不是被检测出来，因为检测它需要的正是这套设计所去除的那次测量。

测试套件只钉住标记结构。jsdom 不解析布局，因此规则本身——各下限、让位顺序、过滚——在浏览器中验证并记录于上表；轨道模板的回归能通过单元测试。这是一处有意的划分，而不是一道该用无头布局引擎去补的缺口：这些论断谈的是真实引擎如何处理内在尺寸。
