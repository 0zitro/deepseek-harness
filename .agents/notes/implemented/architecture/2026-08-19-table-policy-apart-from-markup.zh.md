# Agent Note: 表格的排序与调宽属于策略，而非标记

Status: implemented

[English](2026-08-19-table-policy-apart-from-markup.md) | 中文

## 问题

键位设置页面手工长出了一张可排序、可调宽的表格，而它的每一个部件都住在 `ui-keybindings` 里：排序状态机、行的排序、分隔条的算术、轨道、通道、行分组，以及新增与删除绑定的那些条带。这些没有一样是关于键位的。客户端里再出现第二张表格，就得把同样的部件再长一遍，然后两者开始漂移——而这漂移的最初征兆在这一张表格里已经看得见了：同一份预留曾在两处界面上以两种不同形态被表述。

不过这些部件在种类上并不相同，而把它们混作一团，正是表格难以复用的原因。决定哪些行排在前面，是对值做的算术。决定一列不可被拖到多窄，是对页面做的测量。决定条带悬挂在哪里，是标记。只有第一项完全不依赖浏览器，而它恰恰是消费方最可能想要另行表述的那一项。

## 决定

算术移到 `ui-primitives`，成为两个不含 React、也不碰 DOM 的模块，对行类型泛型化；领域相关的部分留在原处。

`table-order` 装的是排序状态机与排序本身。列不携带比较逻辑；它通过一个 `Ordering<T>` 声明自己持有哪种值，而这种值同时携带比较方式与首次点击所取的方向。`orderedBy` 把"列从哪里读取自己的值"与"这种值如何排序"绑在一起，并就地消掉 `T`，使得一张表的各列保持为同一个 `TableColumn<Row>[]`，而不是任何数组都装不下的一族形状。消费方自己的列类型则在 `TableColumn<Row>` 之上扩展出用于绘制表头的东西，而那是排序无从知晓、也不该知晓的：`ui-keybindings` 的 `SortableColumn` 只添了一个字典键，别无其他，它的 `sortable()` 如今只是在 `orderedBy` 之上的一次展开。

留在 `ui-keybindings` 的，是只有该领域才能表述的东西——手势按它收尾的那个键排序，于是同一个键上的每条绑定都会聚到一起，无论各自带着什么修饰键；来源按优先次序而非字母排序；排序中的位次从胜出的那条绑定数起，而被覆盖的绑定不占位次。这些从来就不通用，也不是第二张表格会想要的部分。

`table-resize` 原封不动地装着 `resizeWidths`。它本来就把下限当作数据接收、而不自己去测量，其文档也早已说明了缘由：一列不可被拖到多窄，是对该列内容的一次测量，而不是这套算术的性质。

最后这一点，正是几何层接手策略的地方。"一列不可被拖到比它的表头更窄"是这张表格的选择，不是通用规则——它的行是有意不算数的，因为行内字段会裁切、手势会滚动，所以不能让一条长子句为本有去处的内容把整列撑开。而以行为主角的表格想要的恰恰相反。

因此 `Table` 接收一个 `floorOf`，在边界被抓住的那一刻询问一次，以便它可以测量；其默认值是该列各单元格在最窄时测得的宽度——即一列展示自己的内容，这是一条应当在知情之下才去偏离的、不出人意料的规则，而不是稀里糊涂就落到手里的那条省着来的规则。`minContentWidth` 被导出，使得一条策略只需一行。

"让单元格自己去声明"这条路已经实测并被否决。`minmax(auto, Xfr)` 的轨道以自动最小尺寸兜底，而任何会裁切或滚动的单元格都会放弃它，于是"行不算数"本可以由行自己来声明，表格也就完全不必长出这个选项。但它在这里行不通：这张表格的**表头**同样是有意裁切的，好让被拖到比自己标签更窄的列作省略号处理，而不是拒绝变窄、从而破坏那一对列的守恒。针对真实的各列实测：`minmax(min-content, Xfr)` 的下限为 `316.42 / 14 / 313.30 / 14 / 40.28`，而 `minmax(auto, Xfr)` 为 `0 / 14 / 0 / 14 / 0`——每一列连同它的表头都归零。同一次探测还带出一件事：下限有两个而不是一个。轨道以 min-content 兜底，因此容不下的面板会滚动而不是裁切；而拖动以策略为下限，且可以更为节省。两者回答的是不同的问题，表格把两者都担着。

### 各项特性借坐标系组合

表格唯一共享的资源是它的坐标系：列线、通道线，以及由各列与任何已确定宽度算出的轨道模板。除此之外的一切，要么是对消费方所持有的行做的算术，要么是占据该网格中某个具名区域的一个元素、外加不属于任何其他人的交互状态。于是一项特性只要指得出自己的区域就能组合进来，而 `Table` 收缩为仅剩坐标系——没有分隔条，没有调宽状态，没有下限策略。

每项特性都是一个三元组，其中任何一条腿在不需要时都可以缺席。排序只有一个纯模块，别无其他，因为排序状态是消费方的 `useState`，表头是消费方的标记。调宽有一个纯模块、一个持有各宽度的钩子，以及 `TableSash`——它是一个库提供的元素，而不是一包待展开的 props，因为边界的标记没有任何消费方差异：role、朝向、可获得焦点、以及指针捕获的处理都是不变的。合并行只有一个纯模块，因为跨行单元格是由该模块摆放的、消费方自己的 div。

各宽度不是被镜像的状态：没有别人持有它们，而不提供调宽的表格根本一个都不持有。要在会话之间保留布局的消费方声明 `initialWidths`，并在一次手势结束时收到 `onWidthsCommit`——那是宽度唯一称得上"是某人所作决定"的时刻，因为拖动会途经两端之间的每一个宽度。

被否决的方案，以及各自在这里的代价。用一个 `features: [...]` 数组去扩展一个 table 实例（TanStack 的形态），会把行模型、排序状态与列尺寸聚合成消费方所持之物的第二份副本，这正是"禁止镜像状态"的逐字违反；它还让"这张表格能做什么"在调用点上不可见，并把各特性在场与否的分支乘积塞进同一个组件里。带隐式 context 的复合组件，会在这张表格已有的那条可见约定旁边再加一条隐藏通道，而位于 provider 之外的子组件会安静地失败、而不是响亮地失败。render props 是把对数据的控制权反转，而这张表格并不持有数据。剩下的就是朴素组合，它诚实的代价是每项特性在调用点上多几行接线，以及库无法强制它从未见过的跨特性不变量——想要打包好的表格的消费方，把那个组合体写一次即可，而什么都不想要的表格从不为此付费。

### 位于单元格之间的控件

新增与删除绑定的那些条带，看上去最不像是表格该管的事，实际上却最明白地正是它该管的。把它们还原成其构成之物：两者都是占据表格本已预留之空间的可交互区域，其尺寸完全来自表格自己的那些私有长度——行间隙、通道宽度、单元格内缩。谁拥有这些长度，谁就拥有由它们构成的那些可操作物。把条带留给消费方，就意味着必须把表格的内部几何作为公共 API 承诺出去，好让消费方的 CSS 够得着它——那是一份比直接发布两个元素更容易泄漏的约定。

这个通用概念不是"新增"与"删除"。它是表格已经开了头的那一族的补完：住在边界里、而不是住在单元格里的控件。`TableSash` 是列边界的；`TableSeam` 是一组行与下一组行之间那道边界的；`TableGutter` 是行自身边缘的。按下它们意味着什么，从不抵达表格，甚至不以具名回调的形式抵达——它们只是带有 label、`onPress` 以及各自所绘内容的按钮。

有一条性质，手工搭的那版靠自律维持，而这里由算术得出。一条通道是 `calc(通道 + gutter)`，分隔条保留通道那一份并把 gutter 那一份作为外边距让出，gutter 取走其余，因此无论两者各自如何设置样式，抓手的像素与 gutter 的像素都不可能重叠。这在这里尤为要紧，因为 gutter 的控件是表格中唯一会销毁东西的那个，而抓手是读者整天瞄准的那个。以 14px 通道加 14px gutter 实测：该轨道解析为 28px，抓手占 289–303，gutter 占 303–317，重叠为零。

跟随指针这一行为，沿着已经确定的那份约定作了切分。条带公布指针沿其自身所处的位置，并夹在自身范围之内；消费方的标记是否按这个偏移量移动，是消费方的一条 `transform` 规则。这个夹取同时也是"停住不动"规则的全部，而不是另立一条关于何时停下的规则：已绘制的条带会在自身之外继续响应，因此位于触及范围内、却已在条带之外的指针会落到最近的一端。用命中测试实测：未绘制的 seam 只在自身范围内响应，已绘制的则在 6px 之外仍响应、而 14px 之外不再响应。

### 样式约定

一个布局组件最难的问题不是它画什么，而是消费方可以改动什么却不至于把它弄坏，而这里的答案是两个层面。表格**会读回**的东西是数据，经由 props 传入——各列、各自的份额、下限策略——因为拖动会把份额换算成像素，而只有画笔知道的份额，会是表格在从未见过的情况下去换算的一个数字。表格**永不读取**的东西是呈现，留在 CSS 里，通过每个部件一个类、以及每个部件以 `data-` 属性公布的状态来触及。

夹在两者之间的，是表格必须知道、却并无主张的那几个长度：通道的宽度与行间的间隙。它们是注册过的自定义属性，因此一个并非长度的值会回退到声明好的初始值，而不是在计算值阶段失效并连带把轨道模板一起拖垮；也因此，什么都不配置时表格照样工作。每条通道还会先读取一条带索引的覆盖值再退回共享宽度——`var(--dsh-table-lane-0, var(--dsh-table-lane))`——这正是某一条通道为容纳行自己的控件而变宽的方式，而无需表格为此长出一个 prop。

表格自身的规则坐落在一个级联层里，因此消费方任何未分层的规则都会获胜，无论其特异性如何：一个去猜特异性的库，就是一个会被消费方对着打的库。唯一的例外是轨道模板，它以内联方式设置，因为它是从 props 计算出来的——样式表若不把数据再陈述一遍就写不出它；内联同时也把它放到了任何会破坏这套算术的规则够不着的地方。

## 考虑过的替代方案

- **把策略留在 `ui-keybindings` 里对外导出**：否决——第二张表格将为了一套与键位毫无关系的算术而依赖键位包，而且一旦有别的东西也需要它，这个依赖的方向就完全反了。
- **由一个 `Table` 组件在内部持有排序**：否决——排序状态属于消费方，由它持久化、由它播种、也由它在自己的测试里负责。组件若持有它，就得再通过一组镜像它的 props 把它暴露回去，而镜像正是会变陈旧的那个东西。
- **让 `SortableColumn` 保持为同时携带排序与表头的单一类型**：否决——表头在这里是一个字典键，换个地方就会是一个节点、一个字符串或一个渲染函数。扩展这个泛型列只花掉消费方一行，却能让排序不必背上一个它根本用不到的类型。
- **用一个主题对象、或一个装着内联样式对象的 `styles` prop**：否决——内联样式除 `!important` 外压过每一条样式表规则，因此一个把消费方的装饰写成内联的组件，等于夺走了消费方自己的级联。它还把颜色与字体塞进了一个 JavaScript 包，而样式表本来就把它们带得更好。
- **完全不发布 CSS，让消费方自己写轨道**：否决——轨道就是那套算术。消费方若要写 `grid-template-columns`，就得把份额、通道宽度与二者的交错一并重述一遍，而拖动届时换算的将是无人达成一致的数字。
- **用 `:where()` 把特异性归零，而不是用级联层**：作为退路保留，而不是作为机制。`:where()` 能让一条规则输给任何指名了什么的消费方规则，但它表达不了两条库内规则之间的先后，而且它是一种逐选择器的自律，一条忘了写的规则就能把它破掉。级联层则把这层关系为整张样式表一次说清。
- **改用部件名属性（`::part` 那一路）而不是每个部件一个类**：在此否决——`::part` 是跨越 shadow DOM 边界的机制，而这里并没有这样一条边界，因此它只会是一条背后没有任何强制力的约定。类会经过消费方自己的构建，而它的设计 token 本来就在那里。
- **把各个具体的排序也一并移走**：除 `byText` 之外一概否决。优先次序、手势与位次都是关于键位的论断；点号分隔的标识符排序或许算通用，但它伸手进了本包的行模型，因此在别处提出需求之前就留在这里。

## 影响

`ui-keybindings` 保住了自己的领域，卸下了那套机械：`sorting.ts` 如今就是各列及其排序，而 `resize.ts` 已经不在了。排序状态机与行的排序在它们现在所住的地方被覆盖，所针对的是一张由运行名称与时长构成的表格、而不是键位——正是这样的覆盖才证明它们是通用的；键位那份测试则只保留关于它自己各列含义的断言。

边界如今是一个可获得焦点、会报告自己所处位置、并可用方向键以及 Home 与 End 移动的 `separator`。这并不是把什么东西移植过来：手工搭的分隔条只认指针，宽度因而不是键盘能够陈述的东西，而同一套算术把两者都答上了。

把最初那版几何对着它所服务的消费方通读一遍，发现了三个缺陷，其中一个只有浏览器才显示得出来。写作 `grid-row: 1 / -1` 的分隔条，其 `-1` 是相对**显式**网格解析的，而行是隐式的表格并没有显式网格——实测下来，该分隔条在一张 114px 高的表格里只有 22px，即一行表头的高度，而写成显式跨度则是 90px。跨度如今是一个 prop，这也正是它诚实的归属：一张表格有多少行，是只有它的消费方才知道的那个事实。拖动此前只在 `pointerup` 时结束，于是被系统夺走的那种拖动——来了个电话、笔离开了数位板——会让表格继续听下去；现在每一种结束方式都走同一条路径。而对已确定模板的读取此前假定了像素，但仍写作 `minmax(min-content, 2fr)` 的模板并不是：它自身带有空格，按位置去读毫无意义，因此 `settledWidths` 宁可什么都不答，也不返回一串 `NaN`，而没有起点可依的手势就不会启动。

合并行是第三个纯模块。`runsBy` 把呈现出的各行切分为键相等的极大相邻片段，这是相邻分组、而不是关系型的那种——而这一区分就是它的全部，因为合并行是关于读者所选顺序的事实，不是关于数据的事实。因此，把两个键交错开来的排序会得到四个连续段，而未排序的表格只有两个；同一个值被读到两次，是呈现在如实陈述，而不是有待复原的缺陷。`runId` 把连续段命名为 `${ordinal}:${key}`，序号在前，好让一个可以自由拼写分隔符的键无法与邻居相撞；该身份在段内编辑、行加入或离开该段、以及另一个键做的任何事情之下都保持稳定。它唯一的残余在模块里写明了：序号表示的是"该键自上而下的第 n 个片段"，因此在新顺序下重新切分，可能会把段级状态落到另一个片段上——这正是为什么行级状态应当住在以行为键的子树里，而消费方本来就是这么做的。

留给消费方的，是表格看不见的一切：哪些行提供哪种可操作物、各种标记与颜色、把标记按所公布偏移量移动的那条规则，以及——由于表格看不见连续段——"每个连续段一条 seam、而不是每条边界一条"这件事。最后这一条是文档而非构造，也正是一张永远不去了解自己各行含义的表格所付出的诚实代价。每条边界一条的方案已被否决：一条依赖指针位于自己哪一半来决定归属哪一组的条带，读起来两组都不像。

`KeybindingsSection` 如今已重建在这一切之上，它卸下的是整套机械：连续段构建器、列线与通道线的算术、轨道模板、下限测量、拖动、子行，以及两条条带。它保留下来的，是只有它才知道的东西——每一列希望有多宽、一列的下限是它的表头本身、一次手势按什么排序，以及新增或删除一条绑定意味着什么。样式表卸下了自己那份轨道列表与四个自定义属性，改为陈述表格的那些长度。

重建之后在页面上实测：各列读数为 `216.906 / 140.344 / 261.016 / 71.1719 / 76.5625`，与手工搭的那张表格给出的完全一致，且贯穿未排序、一个排序、两个排序以及全部撤销四种状态。第一条通道解析为 28，而其余为 14——它是抓手加上 gutter；抓手与删除绑定的那个控件重叠为零。每条边界都纵贯 `1 / span 13`——722 像素高表格中的 714——这正是那个 `1 / -1` 缺陷在真实场景中、而非在探针里被修好。

还有一处改动是任何测试都没有要求的。列标题此前把自己的排序方向写进了可访问名称里，于是读者听到的按钮名是"Priority: ascending"，而当它改变时却什么也听不到。方向如今是表头单元格上的 `aria-sort`，那本来就是它一直所是的那种状态。
