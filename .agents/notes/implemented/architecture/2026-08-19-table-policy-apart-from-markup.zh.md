# Agent Note: 表格的排序与调宽属于策略，而非标记

Status: implemented

[English](2026-08-19-table-policy-apart-from-markup.md) | 中文

## 问题

键位设置页面手工长出了一张可排序、可调宽的表格，而它的每一个部件都住在 `ui-keybindings` 里：排序状态机、行的排序、分隔条的算术、轨道、通道、行分组，以及新增与删除绑定的那些条带。这些没有一样是关于键位的。客户端里再出现第二张表格，就得把同样的部件再长一遍，然后两者开始漂移——而这漂移的最初征兆在这一张表格里已经看得见了：同一份预留曾在两处界面上以两种不同形态被表述。

不过这些部件在种类上并不相同，而把它们混作一团，正是表格难以复用的原因。决定哪些行排在前面，是对值做的算术。决定一列不可被拖到多窄，是对页面做的测量。决定条带悬挂在哪里，是标记。只有第一项完全不依赖浏览器，而它恰恰是消费方最可能想要另行表述的那一项。

## 决定

算术移到 `ui-primitives`，成为两个不含 React、也不碰 DOM 的模块，对行类型泛型化；领域相关的部分留在原处。

`table-order` 装的是排序状态机与排序本身。列不携带比较逻辑；它通过一个 `Ordering<T>` 声明自己持有哪种值，而这种值同时携带比较方式与首次点击所取的方向。`orderedBy` 把"列从哪里读取自己的值"与"这种值如何排序"绑在一起，并就地消掉 `T`，使得一张表的各列保持为同一个 `TableColumn<Row>[]`，而不是任何数组都装不下的一族形状。消费方自己的列类型则在 `TableColumn<Row>` 之上扩展出用于绘制表头的东西，而那是排序无从知晓、也不该知晓的：`ui-keybindings` 的 `SortableColumn` 只添了一个字典键，别无其他，它的 `sortable()` 如今只是在 `orderedBy` 之上的一次展开。

留在 `ui-keybindings` 的，是只有该领域才能表述的东西——手势按它收尾的那个键排序，于是同一个键上的每条绑定都会聚到一起，无论各自带着什么修饰键；来源按优先次序而非字母排序；排序中的位次从胜出的那条绑定数起，而被覆盖的绑定不占位次。这些从来就不通用，也不是第二张表格会想要的部分。

`table-resize` 原封不动地装着 `resizeWidths`。它本来就把下限当作数据接收、而不自己去测量，其文档也早已说明了缘由：一列不可被拖到多窄，是对该列内容的一次测量，而不是这套算术的性质。

最后这一点，正是几何层接手策略的地方。"一列不可被拖到比它的表头更窄"是这张表格的选择，不是通用规则——它的行是有意不算数的，因为行内字段会裁切、手势会滚动，所以不能让一条长子句为本有去处的内容把整列撑开。而以行为主角的表格想要的恰恰相反。

因此 `Table` 接收一个 `floorOf`，在边界被抓住的那一刻询问一次，以便它可以测量；其默认值是该列各单元格在最窄时测得的宽度——即一列展示自己的内容，这是一条应当在知情之下才去偏离的、不出人意料的规则，而不是稀里糊涂就落到手里的那条省着来的规则。`minContentWidth` 被导出，使得一条策略只需一行。

"让单元格自己去声明"这条路已经实测并被否决。`minmax(auto, Xfr)` 的轨道以自动最小尺寸兜底，而任何会裁切或滚动的单元格都会放弃它，于是"行不算数"本可以由行自己来声明，表格也就完全不必长出这个选项。但它在这里行不通：这张表格的**表头**同样是有意裁切的，好让被拖到比自己标签更窄的列作省略号处理，而不是拒绝变窄、从而破坏那一对列的守恒。针对真实的各列实测：`minmax(min-content, Xfr)` 的下限为 `316.42 / 14 / 313.30 / 14 / 40.28`，而 `minmax(auto, Xfr)` 为 `0 / 14 / 0 / 14 / 0`——每一列连同它的表头都归零。同一次探测还带出一件事：下限有两个而不是一个。轨道以 min-content 兜底，因此容不下的面板会滚动而不是裁切；而拖动以策略为下限，且可以更为节省。两者回答的是不同的问题，表格把两者都担着。

### 样式约定

一个布局组件最难的问题不是它画什么，而是消费方可以改动什么却不至于把它弄坏，而这里的答案是两个层面。表格**会读回**的东西是数据，经由 props 传入——各列、各自的份额、下限策略——因为拖动会把份额换算成像素，而只有画笔知道的份额，会是表格在从未见过的情况下去换算的一个数字。表格**永不读取**的东西是呈现，留在 CSS 里，通过每个部件一个类、以及每个部件以 `data-` 属性公布的状态来触及。

夹在两者之间的，是表格必须知道、却并无主张的那几个长度：通道的宽度与行间的间隙。它们是注册过的自定义属性，因此一个并非长度的值会回退到声明好的初始值，而不是在计算值阶段失效并连带把轨道模板一起拖垮；也因此，什么都不配置时表格照样工作。每条通道还会先读取一条带索引的覆盖值再退回共享宽度——`var(--dsh-table-lane-0, var(--dsh-table-lane))`——这正是某一条通道为容纳行自己的控件而变宽的方式，而无需表格为此长出一个 prop。

表格自身的规则坐落在一个级联层里，因此消费方任何未分层的规则都会获胜，无论其特异性如何：一个去猜特异性的库，就是一个会被消费方对着打的库。唯一的例外是轨道模板，它以内联方式设置，因为它是从 props 计算出来的——样式表若不把数据再陈述一遍就写不出它；内联同时也把它放到了任何会破坏这套算术的规则够不着的地方。

## 考虑过的替代方案

- **把策略留在 `ui-keybindings` 里对外导出**：否决——第二张表格将为了一套与键位毫无关系的算术而依赖键位包，而且一旦有别的东西也需要它，这个依赖的方向就完全反了。
- **由一个 `Table` 组件在内部持有排序**：否决——排序状态属于消费方，由它持久化、由它播种、也由它在自己的测试里负责。组件若持有它，就得再通过一组镜像它的 props 把它暴露回去，而镜像正是会变陈旧的那个东西。
- **让 `SortableColumn` 保持为同时携带排序与表头的单一类型**：否决——表头在这里是一个字典键，换个地方就会是一个节点、一个字符串或一个渲染函数。扩展这个泛型列只花掉消费方一行，却能让排序不必背上一个它根本用不到的类型。
- **用一个主题对象、或一个装着内联样式对象的 `styles` prop**：否决——内联样式除 `!important` 外压过每一条样式表规则，因此一个把消费方的装饰写成内联的组件，等于夺走了消费方自己的级联。它还把颜色与字体塞进了一个 JavaScript 包，而样式表本来就把它们带得更好。
- **完全不发布 CSS，让消费方自己写轨道**：否决——轨道就是那套算术。消费方若要写 `grid-template-columns`，就得把份额、通道宽度与二者的交错一并重述一遍，而拖动届时换算的将是无人达成一致的数字。
- **用 `:where()` 把特异性归零，而不是用级联层**：作为退路保留，而不是作为机制。`:where()` 能让一条规则输给任何指名了什么的消费方规则，但它表达不了两条库内规则之间的先后，而且它是一种逐选择器的自律，一条忘了写的规则就能把它破掉。级联层则把这层关系为整张样式表一次说清。
- **改用部件名属性（`::part` 那一路）而不是每个部件一个类**：在此否决——`::part` 是跨越 shadow DOM 边界的机制，而这里并没有这样一条边界，因此它只会是一条背后没有任何强制力的约定。类会经过消费方自己的构建，而它的设计 token 本来就在那里。
- **把各个具体的排序也一并移走**：除 `byText` 之外一概否决。优先次序、手势与位次都是关于键位的论断；点号分隔的标识符排序或许算通用，但它伸手进了本包的行模型，因此在别处提出需求之前就留在这里。

## 影响

`ui-keybindings` 保住了自己的领域，卸下了那套机械：`sorting.ts` 如今就是各列及其排序，而 `resize.ts` 已经不在了。排序状态机与行的排序在它们现在所住的地方被覆盖，所针对的是一张由运行名称与时长构成的表格、而不是键位——正是这样的覆盖才证明它们是通用的；键位那份测试则只保留关于它自己各列含义的断言。

边界如今是一个可获得焦点、并可用方向键移动的 `separator`。这并不是把什么东西移植过来：手工搭的分隔条只认指针，宽度因而不是键盘能够陈述的东西，而同一套拖动算术把两者都答上了。

新增与删除绑定的那些条带将在各自的 cut 中跟进，随后是把该分区重建在成果之上。在那之前，`KeybindingsSection` 仍持有它自己那份几何，本 cut 不改动它。
