# Agent Note: A settings namespace is served by the gateway, not by registering it

Status: implemented

[English](2026-08-17-settings-namespace-exposure.md) | 中文

## Problem

快捷键设置页绑定了自己的命名空间，渲染出每一个字段，接受每一次编辑，却什么都没存下。重新加载后回来的是随包提供的默认绑定，而任何地方都没有报错：控制台没有，页面上没有，宿主日志里也没有。该插件做的正是设置 seam 文档所写的事——`ctx.settingsScope.bind({ namespace })`——而这是必要条件，却并不充分，因为 API 网关只对一份显式 allowlist 提供服务，不在其中的命名空间既不会出现在任何描述结果里，写入也会被一律拒绝。`ui-keybindings` 当时不在那份名单上。

这次拒绝在两个层面上都不可见，而每一层单独看都像是正确的设计。已绑定的 scope 会把非 ok 的描述结果转成一次重新读取，因为通常的成因是连接尚未就绪。发起写入的调用方丢弃了返回的 promise，因为从行的角度看写入本就是发出即忘。两者组合之后，一个权威的「该命名空间未被暴露」答复变成了一次从不上报的重试，留下的唯一症状是偏好设置活不过一次重新加载——而这读起来像是该功能的持久化缺陷，而不是这套组合的配置错误。

页面当时还采用乐观发布：一次编辑一经做出就出现在列表中。这正是即便用户全程盯着、失败仍然无声的原因，因为他们键入的值留在屏幕上的样子，与写入真正落地时一模一样。

## Decision

网关现在服务 `ui-keybindings`，与它早已暴露的其余 Web 偏好命名空间并列。在客户端注册一个命名空间仍然不等于暴露它；allowlist 依旧是决策点，因为那正是授予远程可读与可写权限的边界。

已绑定的 scope 现在会在第一次读到不含该命名空间的描述结果时，以一条指名该命名空间的错误上报此事，且只上报一次。只上报一次，是因为这是一个关于组合方式的事实而非瞬态状况，每次重连都重复只会把它淹没。远程浏览器按设计以 memory 模式绑定，从不上报，因此这条诊断只在确实预期该命名空间会被服务的地方触发。

快捷键 store 也不再乐观发布：它只投影已存储的列表，别的一概不投影，因此一次编辑是在被存下时出现，而不是在被做出时出现。被宿主拒绝的写入再也无法在界面上留下一条重新加载后不复存在的绑定；每次写入都从已存储的列表推导出下一份列表——一旦没有已存储的列表，该写入直接报错拒绝，而不是被允许替换掉它从未见过的那些覆盖项。

## Alternatives considered

- **服务客户端注册的每一个命名空间**：否决——allowlist 是整个配置面的安全边界。注册发生在浏览器中，让注册本身就授予远程读写权限，意味着任何客户端插件都能靠声明把宿主状态暴露出去。
- **让 bind 失败，或在第一次写入被拒时抛错**：否决——远程浏览器合法地绑定网关不会服务的命名空间，并在 memory 模式下工作。抛出异常会为了报告一个只适用于回环组合的部署错误，破坏这个受支持的场景。
- **每次描述被拒都上报**：否决——该状况在两次重连之间不会改变，重复只增加数量而不增加信息，而唯一有用的那一次是第一次。
- **用门禁断言每个客户端注册的命名空间都已暴露**：未实现。注册是浏览器平面的运行时事实，allowlist 则是宿主平面的字面量，因此并不存在一对可比对的静态列表；检查必须启动一套组合并 diff 其描述结果。这里把它记为暂缓事项而非默默留白，因为对下一个客户端命名空间而言，这种「按构造不可见」的失败模式依然存在。

## Consequences

这类失败值得被点名：一次被重试与被丢弃的 promise 共同吞掉的拒绝，会产出一个看起来已实现、却什么都不存的功能，而针对任一侧的测试都不会失败。真正解决它的，是让权威答复在能够区分「尚未就绪」与「此处不服务」的那一层上，把这件事说出来一次。

只投影已存储的状态，代价是页面失去了乐观回声——一次编辑现在要在一个往返之后才出现——换来的是屏幕上所见即已存储的保证。设置界面的其余部分保持各自的行为；本次改动的范围限于快捷键 store 与共享 scope 的上报。
