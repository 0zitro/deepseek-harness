# @deepseek-ai/dsh-client-ui-keybindings

[English](README.md) | 中文

快捷键编排器。客户端侧提供 `uiActions` 注册表，功能包在其中注册动作（action：id、标签、默认绑定，以及一个 `run` 处理器）；它在 `ui-keybindings` 设置命名空间中，为每个被调整过的默认绑定持久化一条局部覆盖项（override：`{ action, key, base, strokes?, when?, prio? }`），把生效的绑定渲染成表格，并把击键分发给匹配动作的处理器。注册方自行声明带 brand 的动作 id 与默认键；这些 brand 经 type-only import 抵达注册方，而跨插件的值导入正是客户端 bundle 所禁止的。

渲染出来的列表只投影已存储的覆盖项，别的一概不投影：因此一次编辑是在被存下时出现，而不是在被做出时出现，被 Host 拒绝的写入也就无法在界面上留下一条重新加载后不复存在的绑定。每次写入都从已存储的列表推导出下一份列表；一旦没有已存储的列表——未读到、未提供服务或无法解码——就没有可推导的依据，于是该写入直接报错拒绝，而不是被允许替换掉它从未见过的那些覆盖项。

已存储的 base 会与外界持续对齐：只要注册方或持久化数据任一侧发生移动，凡是其默认绑定如今携带不同手势的覆盖项，都会把那个默认绑定写回自己的 base，使它合并时所依据的快照始终是来源当前提供的那一份。比较是结构性的，因此对一份已对齐的列表再跑一次不会产生任何写入，这一轮在一次写入之后即告收敛。默认绑定已不可用的覆盖项保留它先前留存的 base——无法对齐并不等于无法合并——而对齐过程从不触碰它已覆盖的那些字段。

贡献方从不自述来源。设置文档按定义属于用户，插件的贡献则属于该插件，所以来源是在读入时打上的——文档一律标记为 `user`——一份声明无从主张自己并不具备的来源。合并谁仍由排名决定：用户高于插件，插件高于随包提供的默认绑定，且只有排名最高的那一条参与合并，绝不会把三者揉在一起。插件可以贡献覆盖项；它不可以自称用户。写回的只有用户自己的文档，因此对齐已存储的 base 不会触碰插件贡献的任何内容。

一次编辑只携带用户改动过的字段，并合并进已存储的覆盖项，而不是替换它。因此录制一个手势之后，`when` 子句仍然不出现在覆盖项中，绑定继续跟随其默认绑定的子句，日后对该默认绑定的改动依然能抵达合并后的绑定；若把合并后的值重述一遍，反而会把它冻住。用户主动清空的子句以空字符串存储，它不声明任何谓词、始终生效——这是覆盖项去掉默认绑定所带子句的唯一途径。

每一对列之间由一条分隔条（sash）划分：它是网格中的一条通道，纵贯表头与其下每一行，归属于边界本身而非任一侧邻居，且整条通道同宽，因此沿线任意位置都能抓取——它绘制的线比捕获指针的抓取区更细，且仅在指针位于其上或正拖动它时才出现。拖动一条分隔条移动的是这一对列共同持有的宽度：一列所得即另一列所失，两者都不会低于各自的下限，因此被拖到极窄的列仍然够得着。守恒以像素计，因为只有在每一列都高于其内容下限时，份额才能映射为宽度——一旦某列被挤到该下限，它交不出去的那部分空间就会重新分给其余列，从而移动了这次拖动根本没碰过的列，并改变表格自身的宽度。拖动止于该列自己的表头——标签，加上它为标记保留的那份空间——不再更窄。各行对这个下限没有发言权：行内字段会裁切、手势会滚动，因此若让一条长子句说了算，就会为本有去处的内容把整列撑开。这个下限在分隔条被抓住的那一刻从表头实测得出，而不是假定，因此这里没有任何数字会与样式表脱节，也不会有哪一列被属于更宽的列的下限撑大。在分隔条第一次被抓住之前，各列自行布局，拖动从那一刻测得的宽度开始，因此没有任何跳动。

点击列表头即按该列排序，各列按点击顺序累积，因此最先点击的那列始终最重要；一旦有多列参与排序，每个标记旁会出现次序编号。再次点击反转该列，双击将它移出排序——组成这次双击的两次单击会先各自切换该列，随后被这次移除丢弃，因此没有任何一次点击需要被压住等待，去确认它属于哪种手势。列本身不携带比较逻辑：它声明自己持有哪种值，而这种值携带排序方式与首次点击的方向。正因如此，来源按优先次序而非字母排序，命令按点号分隔的各段排序，手势按它收尾的那个键排序，于是同一个键上的每条绑定都会聚到一起，无论它各自带着什么修饰键。排序是稳定的，因此某个排序无法区分的行保持它们进入时的次序，同一命令的各行只要在该排序下仍然相邻，就保持相邻。表头是一个在行内末端预留空间的 run：标签是它的内容，而一列所能携带的最宽标记——带着该排序会给最后一列的那个排名——是它的 reserve，隐藏渲染以便由引擎测量，因此这里没有任何宽度是以数字写出的。这个 run 所索要的，在任何状态下都是该标签加上那份空间，正是这一点使得列在加入或退出排序时不改变宽度。标签落在哪里则单独决定，且只取决于实际画出了什么：没有标记时，它在整列范围内居中；有标记时，它偏离居中，偏离量恰为标记所需而不再多——已处于下限的列偏离整整半份空间，尚有余地的列偏离更少，而余地足有一个标记那么宽的列则完全不动。因此列变窄时表头按固定次序让出：先保证标签读得出，再谈与标记保持间隙，最后才谈居中。标签与标记之间的间隙是标记自己的前导内边距，因此它随标记一同被预留、而不是并排在旁，于是在侧翼已经坍缩之处它依然存在。只在画出标记时才预留，看着更省，其实不然：已经处于下限的列没有地方去找标记所需的空间，于是它一被排序就会从邻居那里拿。

子句采用代码字体，因为它靠标点阅读；来源列则把它的短值居中。优先级是一个数字字段，编辑期间允许为空：什么都不填是一次被放弃的编辑，而不是错误，因此该字段在失焦时不作任何抱怨地退回已存储的值，而一个无法在排序中占位的值会被标红并且不予提交。

每个字段都在失焦时提交，因此半截输入的值绝不会被存储、绝不会被分发、也绝不会到达另一个客户端；未经编辑的草稿不提交任何内容，而在字段之下被改动的草稿会被替换。无法解析的子句会被标红且不予提交，因为存下它会解析为假，从而停用它所属的绑定。按键录制器是唯一的例外：手势没有有意义的中间形态，因此它在录制结束时提交。`when` 子句针对 `uiWhenContext` 求值，那是一张由焦点作用域栈（`<FocusScope>`／`data-focus-scope`）与显式状态键共同派生出的映射。Host 侧负责注册该设置命名空间。

领域模型（`keybinding.ts`）由录制器、持久化 schema 与消费方共享：一条快捷键是一列有序的击键——一次击键是简单绑定，两次及以上是组合键（chord）——每次击键由一个非修饰键加一个可选的修饰键集合构成。可选的 `when` 子句（`when-clause.ts`）用 VSCode 语法（`&&`、`||`、`!`、`==`、`!=`、`=~` 与圆括号）把绑定谓词化到界面状态之上。匹配对修饰键严格相等，因此绑定的 `Ctrl+Enter` 在同时按住 `Alt` 时不会触发。单字母键一律以小写持久化，因此无论捕获时是否按住 Shift，同一个字母录制出的结果都相同。

整个页面是覆盖所有行的一张网格——命令单元格纵跨它所拥有的那些行，这是任何逐行元素都做不到的——共五列：命令、快捷键、`when` 子句、优先级、来源。同一命令的各行彼此相邻，因为行按动作 id 的点号分段排序，命令因此只书写一次，在它的行段上居中。每一列都在两个宽度之间调和——它想要的份额，以及它不能低于的下限，即表头加上排序标记所需的空间——因此过长的标签或子句在自己的单元格内换行，而不是把行撑得超出面板，面板窄到容不下这些下限时则整体滚动，而不是溢出。用户覆盖过的字段以斜体渲染，仍跟随默认绑定的字段则后退，这与已存储覆盖项所划出的区分是同一条。行上显示的优先级正是分发用来了结冲突的那一个——覆盖项声明的值，或者它在真正可能与之冲突的那些绑定中所处的位置。优先级只区分共享同一 `(stroke, source)` 的条目，此外别无所指，因此不与任何绑定竞争的绑定读作 0，只有真实的竞争才会往上计数；若按整份列表播种，就会给彼此从不相遇的绑定编号，并且由于每个播种值都互不相同，真实的冲突反而无从察觉。声明出来的优先级是用户的选择，必须成立；播种填补它留下的空位，从低到高，因此未声明的绑定绝不会落到已被占用的位置上。只有非负整数会被存储。

声明优先级是把绑定放到那个位置，而不是提出一个可能被拒绝的主张：它取得该值，同一作用域内排在该位置及其之后的每条绑定都后退一位。共享该作用域的只有用户已经覆盖过的绑定，因此这种位移改写的是已经存在的覆盖项，绝不会替随包提供的绑定或插件贡献的绑定凭空造出一条；播种值无需改写，因为播种本就填在声明值留下的空位里。命令已不再注册的绑定无法使用排序中的位置，于是它交出自己的优先级，而不是占住一个。它没有交出的是 seat：一条不声明任何字段的覆盖项并不是空的，因为占住一个 seat 本身就是一种声明——从此这条绑定属于用户，高于它先前跟随的来源，并在用户的作用域而非那个来源的作用域中排序。以这种方式接管一个默认绑定，会把它从随包提供的作用域挪进用户的作用域，而那里的位置早已被占——这正是为什么位置要放在这次编辑将会留下的世界里判定，而不是在它抵达时的世界里判定。来源要么是随包提供的默认绑定，要么是用户，要么是以自身 id 具名的贡献插件。

覆盖项不会替换 seat 所提供的绑定；它是从后者手中接过这个 seat，而页面把两者都显示出来。随包提供的那条绑定就显示在实际分发的那条之上，带删除线且不提供任何控件，因为它正是覆盖项出发时的那条绑定、也是覆盖项消失后会回来的那一条，并且编辑它只会写到已经占住该 seat 的那条覆盖项上。只有实际分发的绑定才占据位置，因此被取代的行不声明优先级，也不消耗其冲突作用域中的任何空位；在按优先级排序的表格里，它排在每一条持有位置的行之后。不提供任何手势的 seat 只显示一行，因为在那里本该位于覆盖项之上的东西是这个 seat 本身，而不是一条绑定。

新增绑定的入口位于某个命令的最后一条绑定与下一个命令的第一条绑定之间、任何盒子都不占据的那片空隙：一条条带悬挂在该命令所拥有的最后一条绑定之下，悬停时它会画出新绑定将要落到的那条线，画在指针所在处而不是条带所在处——线会随指针在条带内移动，正是这一点让它读起来像绑定将要落下的位置，而不是行上的一件固定装饰。条带本身就是控件：沿线任意处按下都会新增绑定，而不仅限于线中间的那个标记；该标记取用编辑器发送按钮与光标所用的强调色，因为它是表格中唯一会新增内容的东西。已画出的条带触及范围也比它标出的线更宽——两侧各十像素——因此指针可以离开那条线而不失去它，并从这片更宽的空间里按下；与此同时线本身停在原处，不再跟随一个已经离开的指针。这段触及范围只在条带被画出后才存在，因此在指针主动招呼这条条带之前，上下两侧的盒子保有每一个像素；离开该范围，画出的内容随即消失。条带悬挂在那些单元格之下，而不是悬挂在网格行之下，因为一行的高度取决于其中最高的东西——即命令自己的单元格，只要它的描述换到了第二行——那么依附于行绘制的条带就会远远落在它所属的那些盒子之下，反而紧挨着不属于它的那些。因此一条绑定的各个单元格被编成一组，落在表格从第二列起的轨道上，而条带正是从这一组悬挂下来的。每个命令只有一条条带，而不是每个边界一条——一条依赖指针位于自己哪一半来决定命令归属的条带，读起来两个命令都不像——所以两个命令交界处的那片空间归属于上方那一个。条带不占用自己的空间，表格因此始终只有其绑定那么高；纵向滚动归它所处的面板所有，这也是表格明确声明自己不纵向滚动的原因，而不是把它交给一个单轴设置下两轴都会滚动的默认行为。提交的只有控件，绝不是整条条带，因为新增目前还无法撤回，而条带所在之处正是一次瞄准盒子的点击可能落空的地方。指针在别处时，条带画出的内容是透明而非隐藏，因为隐藏会连键盘也一并夺走；在被画出之前它不接收任何指针事件，因此被它悬盖的东西仍然够得着。

用户持有的绑定可以再被删除，入口位于该行起始处的那条通道。这条通道被加宽以并排承载两样东西——紧挨着行的、用于删除绑定的边槽（gutter），以及在它之外的分隔条抓取区——因此两者绝不共享哪怕一个像素：一次瞄准列边界的按下，绝不允许落到表格中唯一一个具有破坏性的控件上。该条带纵贯它将要删除的那条绑定的高度，在指针位于边槽内时画出，随指针横向移动，且触及范围不超出自身，因为它两侧一边是列边界，另一边是该行自己的字段。删除会保留 seat 所提供的绑定，因此随包提供的绑定回到页面上，而用户新增的绑定则彻底离开。它只出现在用户持有的绑定上：随包提供的默认绑定与插件的贡献都不由用户处置。

新增的绑定占据一个属于自己的 seat，其键取自它所依附的那个 seat 的家族——`send`，然后 `send#1`、`send#2`——这个后缀是任何注册方都写不出来的，因此新铸的键与随包提供的键无论各自如何变化都不会碰撞。它从那个 seat 的 base 分叉而来，而不是从零开始，因此它的子句跟随它所出自的那条绑定，并且仍可被清空或替换；它声明的手势不含任何击键：它从一开始就属于用户，并在用户录制之前保持惰性。

录制器捕获组合键：点击进入待录状态，随后每次非修饰键的 keydown 追加一次击键，按住的修饰键渲染为按下状态的按键块；录制器内部的对勾提交，Escape 或失焦取消，不带修饰键的 Backspace 删掉最后一次击键，锁定键抬起可复位卡住的修饰键，自动重复的 keydown 一律忽略。当指针位于一个有内容可解绑的录制器上时，同一位置会出现一个叉号，清除后存下的是不含任何击键的手势——空手势无法与任何输入匹配，于是该动作不再绑定到任何按键，而这条绑定仍归用户所有，可以再次录制覆盖。两个控件都是绘制而非书写的，与排序标记共用同一块底板。按键块条是一个在末端为控件预留空间的 run，而这块空间是以控件的一份副本、而非以一个宽度来表述的，因此二者无从不一致——只有控件浮动所依的那点内缩是数字，写在一处，由控件与副本共同读取。无论是否画出控件，条带索要的都是这块空间，因此控件的出现与消失都不会让任何一列移动。按键块落在哪里则是另一个问题，由实际画出了什么来回答：条带之上没有控件时，没有什么需要避让，按键块居中；有控件时，它们偏离居中的量恰为控件所需而不再多——若条带尚有一个控件宽度的余地，则完全不动。宽度超出所在列的手势保持在一行内，靠滚动来阅读，因为换行会加深行高，而裁切则会把击键永久藏起来。控件的空间随控件一同进入可滚动的内容，正是它在滚动到尽头时把最后一次击键从控件底下带出来。它也随控件一同离开，而这会把可滚动范围收缩到读者所在位置之下，于是引擎把偏移量夹紧，位置在任何代码读到它之前就已经消失。因此条带会把自己在该空间尚在时所处的位置记下来，并在该空间回来时把这个位置还回去——连同重叠一起，因为在这么小的余地里，要点本就是什么都不动，而整整移动一个预留空间比让控件压住最后一次击键更难看。若条带在控件离开期间被移动过，那便是读者自己选择的位置，就留在那里。被覆盖绑定那条划掉的按键块条用的是同一个 run、索要同一块预留空间，因此两行的按键块落在同一处。击键在 window 上捕获，因此焦点无关紧要；修饰键状态从 `getModifierState()` 读取，并以布尔标志作为回退。

## 已知限制与暂缓事项

- **子句可以指名哪些状态键，取决于各功能发布了什么，而且没有任何地方枚举它们**：编辑器声明了自己的焦点作用域，并发布 `commandMenuOpen` 与 `tokenLeading`，因此 `composerActive`、`commandMenuOpen`、`tokenLeading` 与 `controlActive` 可以求值；指名其他键的子句不会被拒绝，它只是永远不成立。设置字段无法提供一份它列不出来的清单。
- **无法通过拖动行来重排绑定**：在冲突作用域内放置一条绑定，目前只能靠声明优先级，而已声明的优先级无法再撤回：缺席意味着未声明，因此一个值可以被改动，却无法退回它原本所处的播种状态。
- **Linux 上的 Firefox 会过滤内容页面的修饰键事件**：组合 keydown 中不含 `Alt`，单独的修饰键 keydown 也从不派发给 `http` 页面（它们确实能到达特权的 `about:` 页面），因此 `Alt` 组合键与按键前的修饰键预览在那里不可用；Chromium 正常。录制器本就优先使用 `getModifierState()`；这些事件是缺席，而不仅仅是标志位有误。
